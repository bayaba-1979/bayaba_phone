📡 S21 ↔ WSL — 2트랙 티스토리 자동화 로드맵

S21 Paste Pipeline(수동 5-Click) → WSL Playwright(완전 무인화)
동일한 설계 원리, 다른 실행 환경. 업그레이드 경로 확보.

🗺️ 두 시스템 한눈에

S21 Paste Pipeline v5.1
환경: proot Ubuntu on Galaxy S21 (aarch64)
방식: LLM 대화 → .md → HTML → TG .txt 전송 → 사람 5-Click
채널: 5 Tistory
장점: Playwright 불필요·경량·S21 온디바이스
제약: 사람 개입 필수·2~3분/건
상태: ✅ 운영 중
WSL Parksy Distributor v1.0
환경: WSL2 Ubuntu (x86_64, Playwright 가능)
방식: generator.py → publisher.py → Playwright → Tistory 자동발행
채널: 21 Tistory + 15 YouTube + 3 Naver + Discord 28
장점: 완전 무인화·MCP 20+도구·멀티플랫폼
제약: WSL 필요·Playwright 의존성 무거움
상태: ⏸️ WSL 머신에서 대기

🏗️ 공유 설계 — 두 시스템을 관통하는 원리

실행 환경이 달라도 설계 원리는 동일하다:

원리S21 구현WSL 구현
2계층 분리Human(LLM·TG·Tistory) / Machine(GitHub·Pages·Actions)Human(LLM·MCP) / Machine(Playwright·Tistory·YouTube API)
양방향 브릿지Paste(내부→외부) + RSS(외부→내부) + Loopback(평가)parksy_distribute_all(내부→외부) + parksy_*_list_*(외부→내부)

단일 진실configs/ecosystem-map.jsonchannel_map.json
MCP 래퍼helena-studio-mcpparksy-distributor (FastMCP)
🔑 핵심: 두 시스템은 같은 설계도의 다른 구현체. S21은 경량·모바일·수동, WSL은 중량·데스크톱·자동. Paste Pipeline의 구조적 발견(루프백·2계층·.txt 표준)은 WSL 버전에도 그대로 적용 가능.

🔄 업그레이드 경로 — S21 → WSL 단계적 전환

단계내용트리거S21 영향
0. 현재S21 Paste Pipeline v5.1 독립 운영—주력
1. 참조WSL 코드베이스 → helena-programming/reference/wsl-automation/완료없음 (문서화)
2. MCP 통합parksy-distributor MCP → helena-studio-mcp에 통합WSL 환경 접근 가능 시MCP 도구 6→26+
3. generator.py 이식파피루스 CSS v4.0 → S21 HTML 변환기로단행본급 발행 필요 시HTML 품질 ↑
4. Hybrid 모드중요 채널=WSL 자동, 일상=S21 수동WSL 안정화 후부하 분산
5. Full WSL모든 발행 WSL에서 자동화, S21=감독·검증·루프백WSL 24/7 가동 시역할 변경 (제작→감독)
⚠️ 중요: WSL로 전환해도 S21은 폐기되지 않는다. S21의 새 역할 = 품질 감독 + 루프백 평가 + 콘텐츠 기획. 발행이라는 기계적 작업에서 해방되어, LLM이 평가한 데이터를 바탕으로 더 나은 콘텐츠를 기획하는 두뇌 역할.

🎯 핵심 정리

S21 = 현재 주력
5채널·Paste Pipeline·수동이지만 작동한다. API 없이도 양방향 루프 완성.
WSL = 미래 확장
21+15+3 채널·Playwright 완전자동·MCP 20도구. 환경 준비되면 즉시 가동.
둘은 경쟁이 아니라 보완
S21=두뇌(기획·평가·루프백), WSL=손(발행·배포·크로스플랫폼). 같은 설계 원리.
코드는 이미 준비됨
WSL 코드 전부 reference/에 보존. 업그레이드 경로 문서화 완료. 환경만 되면 바로.
